# QuickNote — 设计文档

日期：2026-10-05
状态：待评审

## 1. 背景与目标

一款 Windows 11 上的常驻轻量备忘录。开机自启，双击左 Ctrl 唤起一个悬浮小条，把内容按天追加进 markdown 文件。

**使用者**：作者本人，日常自用。
**核心约束**：待机内存必须小。这是唯一不可让步的指标——它决定了所有技术选型。
**成功的样子**：随手记一笔的摩擦低到不需要犹豫；三个月后打开 `notes\` 是一堆可读、可搜索、可用任何 markdown 工具打开的纯文本文件。

**定位：临时备忘录，不是终身档案。** 它的用途是记录当下要记住的事——会议要点、待办、临时结论，用完即弃。这解释了为什么明确不做同步、标签、应用内阅读，也解释了搜索结果上限 200 条是够的。将来若要加功能，先回到这一行确认它是否仍成立。

### 非目标（明确不做）

- 不渲染 markdown 预览。只做写时的语法高亮。
- 搜索结果不在 app 内阅读。选中后走系统默认编辑器打开那天的文件。
- 不做云同步、多设备、加密。
- 不做多标签页、文件夹、标签系统。
- **全文搜索不建索引**（详见第 7 节：日记的规模不需要索引，建索引会直接违反内存约束）。

这些都是好功能，但每一条都会把内存和开发量推上去，且不在"随手记一笔"的主路径上。

## 2. 验收标准

1. 待机私有工作集 **≤ 35MB**（任务管理器"内存"列），超标需排查。
2. 冷启动到托盘就绪 **< 1 秒**。
3. 双击左 Ctrl 弹出小条。正常打字时**不误触发**——尤其 `Ctrl+C`、`Ctrl+V`、`Ctrl+S`。
4. 小条内中文输入法正常工作（候选框、组合键切换均正常）。
5. 进程被强制结束后，当天已保存内容完整可读。
6. `notes\` 下的文件用 Typora / VS Code 打开，渲染正常。
7. 安装钩子后正常打字无可感知延迟；钩子回调平均耗时在微秒级（用 `Stopwatch` 计时并在调试输出中核对）。
8. **搜索期间 UI 不阻塞**：扫描进行时仍能正常打字、切模式、关小条，且全系统键盘不卡顿。
9. **搜索不增加待机内存**：连续搜索十次后，待机私有工作集回到第 1 条的基线，无累积增长。

## 3. 技术选型

**选定：.NET Framework 4.8 + WinForms**

### 为什么

决定性的事实是：**WinForms 官方不支持 NativeAOT**。发布时会被 SDK 拦截（`NETSDK1175: Windows Forms is not supported or recommended with trimming enabled`），绕过需要社区包 `WinFormsComInterop` 加内部 MSBuild 开关 `_SuppressWinFormsTrimError`，官方定位是实验性用途。更关键的是，AOT 环境下 **RichTextBox 会因 COM interop 边界问题失效**——而 RichTextBox 正是语法高亮方案的基础。

绕不过去的三条替代路都堵死：换控件（WinForms 文本编辑全部基于原生控件互操作，同样有风险）、自绘编辑器（光标、选区、中文输入法全要手写）、换 WPF（同样不支持 AOT，内存更大）。

排除 AOT 之后，.NET Framework 4.8 成为最优解，因为它是**系统共享**的：几十个进程共用同一份已 NGEN 编译的 `System.Windows.Forms.dll`，不重复占用物理内存。而 .NET 8 自包含发布要把整个运行时拉进本进程。

### 内存账

| 方案 | 待机私有工作集 | 结论 |
|---|---|---|
| .NET Framework 4.8 + WinForms | 约 20–35MB | **选定** |
| .NET 8 + WinForms（无 AOT） | 约 35–55MB | 卡在预算线上，靠调优去压不打包票 |
| Electron | 150MB+ | 直接排除 |
| Tauri（WebView2） | 80–150MB，多子进程 | 排除 |

### 代价

工具链偏老：用不上现代 C# 语法糖与较新的库。对一个小型自用工具，这个代价可以接受。

### 依赖策略

**除 .NET Framework 自带程序集外，不引入任何第三方依赖。** 配置解析、日志、断言自检全部手写。这样既省内存，也避免了老工具链下的包管理摩擦。

## 5. 数据格式

### 文件命名

`yyyy-MM-dd.md`，例如 `2026-10-05.md`。ISO 日期，字母序等于时间序，便于将来写脚本统计或同步。

### 文件内容

时间戳是**列表项的行首前缀**：

```markdown
# 2026-10-05 星期一

- 14:30 跟老王确认了接口字段

- 14:32 对方说周五之前给答复

## 下午计划

- [ ] 把 spec 写完
- [ ] 回复邮件
```

**单行内容**直接跟在时间戳后面。**多行内容**只有第一行带时间戳前缀，之后的内容原样写入、不做缩进。

缩进续行（把后续行缩进两格使其归属同一条列表项）视觉上更整齐，但会让缩进过的 `## 标题` 退化成普通文字，破坏使用者自己写的 markdown 结构。因此选择不缩进。

### 什么自动、什么手动

这一节明确职责边界：

| 元素 | 谁负责 |
|---|---|
| 时间戳 `- 14:32` | **程序自动**，取保存那一刻的系统时间 |
| 文件标题行 `# 2026-10-05 星期一` | **程序自动**，仅在该文件首次创建时写入 |
| 文件名 `2026-10-05.md` | **程序自动**，按日期推导 |
| 正文内容 | **全部由使用者输入** |

程序**不解析、不补全、不生成任何正文**。它不识别"计划""待办""会议"这类词，不会替使用者填空，也不理解内容含义。使用者在小条里敲的每一个字（时间戳前缀之外）都原样进入文件。

### 规则

| 项 | 取值 | 理由 |
|---|---|---|
| 编码 | UTF-8 **无 BOM** | 带 BOM 时部分工具会在文件头显示乱码 |
| 换行 | LF | 一致、git 友好；现代记事本识别 LF |
| 写入方式 | 追加，不重写整个文件 | 中途崩溃时前面的内容不丢 |
| 文件打开模式 | 共享读写 | 用户正用 Typora 打开当天文件时，本程序仍可写入 |
| 首行 | 文件首次创建时写入 `# yyyy-MM-dd dddd` | 星期用中文，与系统区域设置一致 |
| 空输入 | 不创建文件、不写入 | 误按 Enter 不留痕迹 |
| 跨午夜 | 按**保存那一刻**的日期定位文件 | 小条开着跨过零点时，内容进新的一天 |

### 写入流程

整个过程是**纯追加，写入前不读取文件内容**：

1. 取保存时刻的本地时间。
2. 用该日期推导 `{NotesDir}\yyyy-MM-dd.md`。
3. 目录不存在则创建。
4. 文件不存在则创建并写入标题行。
5. 追加 `- HH:mm ` 加首行内容。
6. 多行内容的第二行起原样追加，不做缩进。
7. 结尾补一个换行。

同一分钟内保存两次会产生两条相同时间戳的记录。这是有意为之——合并逻辑会要求写入前读取文件尾，为一个纯粹的观感问题引入额外代码路径与边界情况，不值得。

## 6. 交互设计

### 小条外观

无边框、圆角、带投影、深色半透明背景的浮动卡片，位于屏幕**上方三分之一**居中。同一个窗口有两种模式，宽度恒定，高度随模式与内容变化。

**记录模式**（默认）

- 尺寸：560px 宽，高度随内容在 3–8 行之间自适应
- 顶部一行：`2026-10-05 星期一` 与 `今天已记 N 条`
- 中部：RichTextBox 输入区，带 markdown 语法高亮
- 底部一行：`Enter 保存 · Shift+Enter 换行 · Tab 搜索`

**搜索模式**

- 尺寸：600px 宽，高度约 10 行
- 顶部一行：搜索图标、查询框、右侧显示 `N 条 · 扫描 M 个文件`
- 中部：结果列表，每条占三行——日期、匹配行（命中处高亮）、上下文行
- 底部一行：`↑↓ 选择 · Enter 打开 · Tab 返回`

**共用外观**

- 圆角：Windows 11 上用 `DwmSetWindowAttribute` 的 `DWMWA_WINDOW_CORNER_PREFERENCE`，由系统绘制
- 投影：窗口类样式 `CS_DROPSHADOW`
- 主题：跟随系统（读 `HKCU\...\Themes\Personalize\AppsUseLightTheme`），托盘菜单可强制浅色/深色
- 不在任务栏显示，只在托盘常驻

### 语法高亮

输入框是 RichTextBox（原生 RichEdit 控件）。文本变更时**整体重扫全文重新着色**——内容只有几百字节，增量高亮的复杂度不值得。

| 语法 | 呈现 |
|---|---|
| `#` / `##` / `###` 开头的行 | 蓝色、加粗 |
| `-` / `*` / `+` 开头的行 | 列表符蓝色 |
| `- [ ]` / `- [x]` | 橙色 |
| `**粗体**` | 字重加粗 |
| `` `代码` `` | 等宽字体 |
| `>` 引用 | 灰色 |

实现注意：**绝不能给 `RichTextBox.Text` 赋值**——那会清空全部格式。只用 `Select(start, length)` + `SelectionColor` 上色。重着色期间必须保存并恢复光标位置与滚动位置，并用 `WM_SETREDRAW` 关闭/开启重绘以消除闪烁。这两个细节不处理的话，直接表现是"打字时光标乱跳"和"每敲一个字闪一下"。

### 键位与进出

| 动作 | 行为 |
|---|---|
| 双击左 Ctrl | 小条在屏幕上方三分之一淡入（约 120ms），输入框聚焦，光标置于末尾 |
| `Enter` | 保存 → 清空 → 淡出隐藏 |
| `Shift+Enter` | 换行，小条随内容长高 |
| `Esc` | 隐藏但**不清空**。下次唤起内容仍在 |
| 失焦 | 隐藏，同样不清空 |
| 托盘"退出" | 有未保存内容时先询问，不直接丢弃 |

`Esc` 与失焦都不清空，是为了防手滑。写过三行东西误按一下就全没了，是最劝退的体验。想丢弃内容时 `Ctrl+A` 删除即可。

**`Enter` 与中文输入法的交互是必须显式处理的路径。** 拼音输入过程中候选框开着时，`Enter` 的语义是"上屏候选词"而非"保存"。正常情况下输入法会在组合状态中吞掉该按键，程序收不到，因此无需额外代码；但这条路径一旦失效，后果是使用者用中文写作时每选一次词就保存并关闭一次，软件完全不可用。实现时必须实测验证，不能假定。

### 模式切换

两种模式用 `Tab` 双向切换。**默认进入记录模式**，不记忆上次的模式——打开小条的主用途是记一笔。

`Tab` 在文本框里本来是缩进键，直接占用会与写嵌套列表冲突。解法是让它在记录模式下**仅在输入框为空时**切换模式：

| 当前状态 | `Tab` 行为 |
|---|---|
| 记录模式，输入框为空 | 切到搜索模式 |
| 记录模式，输入框有内容 | 插入 2 个空格（缩进） |
| 搜索模式 | 切回记录模式 |

这个规则不会误触，因为**按热键弹出小条时输入框必然是空的**——而那正是唯一会想到"我要搜个东西"的时刻。开始打字之后 `Tab` 就完全归缩进使用。至于在空输入框上按 `Tab` 想缩进——想缩进总是先有内容，实际上不会发生。

缩进插入 **2 个空格而非制表符**：markdown 里空格缩进比 `\t` 通用，Typora、VS Code、GitHub 渲染都稳。

搜索模式下 `Tab` 任何时候都能切回：搜索框里的内容没有"缩进"这一概念，不存在冲突。

### 模式状态

切换模式时**各自保留自己的内容**：记录模式下已写的草稿不因切去搜索而丢失，搜索词也不因切回记录而被清空。切回搜索时沿用上次的查询词并保留结果，避免反复输入同一个词。

- 记录模式的草稿：仅在保存成功或使用者手动删除时清空
- 搜索模式的查询词与结果：在小条隐藏时丢弃（下次打开小条是全新的一次查找）

## 7. 全文搜索

### 为什么不建索引

常规做法是倒排索引，但它常驻内存。几百 MB 的笔记就是几十 MB 的索引，直接违反内存约束。

日记这种数据的特性使索引变得不必要：**纯文本、体积小、增长慢**。一天一个文件，三年约一千个文件、合计几 MB。这个规模全量扫描即可，且**待机开销为零**。

### 扫描方式

- **流式**：逐文件、逐行读取，命中即记下「文件 + 行号 + 匹配行 + 上下文行」，随后立刻释放文件内容。任何时刻内存中只有一个文件的内容加结果集，不把全部笔记读进内存。
- **结果上限 200 条**，防止高频词导致结果集膨胀。达到上限即停止扫描，并在 UI 中标注"结果已截断"。
- **顺序**：按文件日期倒序，最近的在最前。
- **范围**：`{NotesDir}\*.md`，不含子目录。

### 匹配规则

**大小写不敏感的子串匹配。** 中文没有词形变化，不需要词干提取或分词；使用者的预期也正是如此——搜"老王"就该出现所有含"老王"的行。英文场景下子串匹配同样够用。这比为支持模糊搜索引入编辑距离算法简单得多，且对中文的实际效果更好。

### 线程与性能

**扫描必须在后台线程执行。** 扫一千个文件需要几百毫秒，若跑在 UI 线程上，由于全局键盘钩子的存在，这几百毫秒内**全系统键盘都会卡顿**（见第 8 节）。

- 输入即搜，**200ms 防抖**：停止输入 200ms 后才发起扫描
- 新一次扫描开始时取消上一次未完成的扫描，避免结果乱序返回
- 扫描期间 UI 显示"搜索中"，仍可正常打字、切模式、关小条
- UI 更新一律通过 `BeginInvoke` 回到 UI 线程，后台线程不直接触碰控件

### 结果的用途

搜索结果是**查找器而非阅读器**。在结果上按 `Enter`，用系统默认编辑器打开那一天的文件。app 自身不提供阅读界面。

这带来一个已知的粗糙点：外部编辑器无法定位到具体行，打开后需要使用者自己在文件里找到那一处。由于单日文件通常只有一屏到几屏，这个代价可以接受。

## 8. 热键系统

### 主路径：双击左 Ctrl

`RegisterHotKey` 只能注册"修饰键 + 键"的组合，无法检测双击。因此必须使用**全局低级键盘钩子**（`SetWindowsHookEx` + `WH_KEYBOARD_LL`）。

这条路的代价必须记录在案：

| 影响 | 说明 |
|---|---|
| 全系统按键延迟 | 每次按键多一次进程间投递，通常 <1ms |
| 进程卡住则键盘卡住 | UI 线程一卡全系统打字都会顿；Windows 超时后会**静默摘掉钩子**，热键失效且无任何提示 |
| 杀软 / 游戏告警 | 低层键盘钩子是键盘记录器的经典手法，部分杀软会报毒，带反作弊的游戏可能拒绝启动 |
| 远程桌面 | 可能不生效 |

选择它的理由是双击 Ctrl 在中文工具圈足够主流（Listary、uTools 等），且是本需求明确指定的交互。

### 性能开销

| 项 | 实际开销 |
|---|---|
| 内存 | 可忽略。钩子只是一次系统调用留下的注册项，回调与时间戳字段是常数级 |
| 待机 CPU | **0**。事件驱动，无按键时不调用，无轮询、无定时器 |
| 按键延迟 | 微秒级。人感知延迟的阈值约 10–50ms，差三个数量级，正常打字无感 |

**但存在一个尾部风险：UI 线程卡多久，全系统键盘就卡多久。**

钩子回调在 UI 线程上执行。若该线程此刻正忙（垃圾回收暂停、死锁、慢 IO），Windows 会一直等待回调返回——而它等待的是整个键盘输入链路上的每一次按键。超过 `LowLevelHooksTimeout`（默认约 300ms）后，Windows 会**静默摘除钩子**，无任何提示，表现为热键突然失效。

因此，稳态下开销可忽略，但程序卡顿的惩罚会被放大到全系统。对策：

- **钩子回调里只做一件事**——记录时间戳并向主窗口投递消息。任何耗时操作（读文件、渲染、弹窗）一律回到消息循环之后执行。
- **本程序几乎不分配内存**（使用者敲入的几百字节），GC 压力极小，因 GC 暂停而阻塞钩子的概率很低。「内存小」这一约束在这里成了意外红利。
- **UI 线程上不挂任何定时器或后台轮询。** 保存时的文件写入是唯一的同步 IO，内容是几 KB 的追加，正常在 1ms 内完成。

**范围**：只认左 Ctrl（`VK_LCONTROL`），右 Ctrl 不响应。避免与占用右 Ctrl 的软件冲突，也减少误触。

### 状态机

这是整个设计里最微妙的一块逻辑。规则：

```
Ctrl 按下        → 标记「本次 Ctrl 未搭配其他键」
期间按下其他键    → 清除标记（这是 Ctrl+C，不是轻点）
Ctrl 抬起        → 若标记仍在，记为一次「轻点」，记时间戳
两次轻点间隔 < 阈值 → 触发
```

没有"期间按下其他键则清除标记"这一条，使用者每按一次 `Ctrl+C` 都会弹出小条。

默认阈值 300ms，可在设置中调整。

### 备用路径

钩子安装失败时应自动降级，注册默认组合键 `Ctrl+Alt+N`（`RegisterHotKey`），并通过托盘气泡告知使用者。否则失败模式是"热键没反应，使用者以为是自己的手抖"——这是最难排查的一类问题。

组合键需避开 `Ctrl+Space` 与 `Ctrl+Shift`：那是中文输入法的切换热键，抢占会导致输入法行为错乱。

### 设置

托盘菜单 →「设置」，弹出对话框可配置：

- 热键模式：双击左 Ctrl / 组合键
- 双击判定窗口（默认 300ms）
- 备用组合键（按下组合键即录制）
- 主题：跟随系统 / 浅色 / 深色

`RegisterHotKey` 返回失败时立刻提示"已被其他程序占用"，不静默失效。

## 9. 开机自启

写入注册表 `HKCU\Software\Microsoft\Windows\CurrentVersion\Run`。

- 不需要管理员权限
- **会出现在任务管理器的"启动"选项卡里**，使用者能自行查看与禁用。这是优点而非缺点。
- 托盘右键提供「开机自启」勾选项控制开关

**路径自查**：注册表存的是 exe 的绝对路径。程序移动位置后，自启会静默失效。因此每次启动都要比对注册表中的路径与自身当前路径，不一致则自动修正。约十行代码，消除一类将来难以定位的问题。

## 10. 单元划分

### QuickNote.Core（纯逻辑，不引用 WinForms）

| 单元 | 职责 | 接口要点 |
|---|---|---|
| `NoteStore` | 文件路径推导、创建、追加 | `Append(string content, DateTime now)` |
| `DoubleTapDetector` | 双击 Ctrl 状态机 | `KeyEvent(KeyAction action, DateTime now) → bool triggered` |
| `NoteSearcher` | 流式扫描并匹配 | `Search(string query, int limit, CancellationToken) → IEnumerable<Hit>` |
| `AppConfig` | 配置读写 | `Load()` / `Save()`，字段为公开属性 |
| `DateFormat` | 时间戳格式化 | `FileName(DateTime)` / `Heading(DateTime)` / `Stamp(DateTime)` |
| `BarMode` | 记录 / 搜索的模式切换规则 | 纯枚举与转移函数，Tab 的判定逻辑在此 |

**这里最重要的一处隔离**：`DoubleTapDetector` 是纯状态机。调用方喂给它「左 Ctrl 按下 / 左 Ctrl 抬起 / 其他键按下」加一个时间戳，它返回是否触发。它完全不知道钩子的存在。于是最微妙的逻辑可以脱离整个系统离线测试，而不是靠手动敲键盘去碰运气。

`NoteSearcher` 同样不依赖 UI：它接收查询词与一个目录路径，返回结果序列。取消与结果上限都是参数。于是"扫到什么、按什么顺序、截断行为是否正确"可以针对临时目录离线验证，不需要跑起界面。

`NoteStore` 与 `NoteSearcher` 都接受注入的 `DateTime`（后者用于结果排序）而非读取系统时钟，以便测试跨天切换与排序稳定性。

### QuickNote（WinForms 界面与系统集成）

| 单元 | 职责 |
|---|---|
| `Program` | 入口、单实例 Mutex、全局异常处理 |
| `KeyboardHook` | `WH_KEYBOARD_LL` 钩子，回调只投递消息 |
| `FallbackHotkey` | `RegisterHotKey` 注册与降级 |
| `CaptureBar` | 无边框 Form、RichTextBox 高亮、键位处理、两模式切换 |
| `SearchController` | 防抖、后台扫描的派发与取消、结果回送 UI 线程 |
| `TrayIcon` | NotifyIcon 与菜单 |
| `AutoStart` | 注册表读写与路径自查 |
| `SettingsDialog` | 设置界面 |
| `Theme` | 系统主题探测与配色表 |

`SearchController` 单独成件，是为了把「防抖、取消上一次扫描、`BeginInvoke` 回 UI 线程」这堆易错的并发细节从界面代码里隔离出去。`CaptureBar` 只负责把查询词交给它、把结果画出来，不碰线程。

### QuickNote.SelfCheck（控制台自检）

普通断言，不引入 xunit / NUnit。这个规模不值得为测试再拖一套依赖进来。一条命令运行，失败时退出码非零。

### 单实例

命名 Mutex。若已有实例在运行，则向旧实例广播自定义消息令其弹出小条，新实例自行退出。否则误双击 exe 会出现两个托盘图标和两个小条。

## 11. 错误处理

| 场景 | 行为 |
|---|---|
| 钩子安装失败 | 自动降级注册备用组合键，托盘气泡告知 |
| **写入文件失败** | **内容绝不清空**。小条内联红字提示加托盘气泡，让使用者能把内容复制走。这是最重要的失败路径——丢数据比任何崩溃都严重 |
| 搜索时个别文件读取失败 | 跳过该文件继续扫描，在结果页脚标注「N 个文件无法读取」。不因单个文件坏掉而让整个搜索失败 |
| 搜索目录不存在或为空 | 显示「没有找到匹配」，不报错 |
| `notes\` 不存在 | 启动时自动创建 |
| 配置文件损坏 | 备份为 `config.bad`，以默认值启动，不崩溃 |
| 未处理异常 | 全局 handler 写入 `%APPDATA%\QuickNote\error.log`，并提示一次 |

## 12. 测试策略

### 自动覆盖（SelfCheck）

**`NoteStore`**
- 新文件创建并写入标题行
- 向已有文件追加
- 跨天切换到新文件
- 多行内容仅首行带时间戳前缀，后续行原样不加缩进
- 时间戳与文件名的格式正确
- 输出为 UTF-8 无 BOM
- 空输入不创建文件

**`DoubleTapDetector`**
- 阈值内两次轻点 → 触发
- 超过阈值 → 不触发
- `Ctrl+C`（Ctrl 抬起前夹了其他键）→ 不触发
- 长按 Ctrl → 不触发
- 右 Ctrl → 不触发
- 两次轻点之间夹了其他键 → 不触发

**`NoteSearcher`**（针对临时目录，写入若干构造好的 `.md` 文件）
- 命中大小写不敏感：搜 `snake` 能匹配 `Snake_Case`
- 中文子串命中：搜「老王」匹配「跟老王确认了接口字段」
- 结果按日期倒序，最近的在最前
- 结果上限生效：构造超过上限的命中，确认被截断且标记为已截断
- 上下文行取自匹配行的相邻行；匹配行在文件首行或末行时不越界
- 非 `.md` 文件与子目录被忽略
- 单个文件读取失败时跳过，其余结果仍正常返回
- 取消令牌触发后迅速返回，不再继续遍历文件

**`BarMode`**
- 记录模式 + 输入框为空 + `Tab` → 搜索模式
- 记录模式 + 输入框有内容 + `Tab` → 保持记录模式（交给缩进处理）
- 搜索模式 + `Tab` → 记录模式

**`AppConfig`**
- 读写往返一致
- 损坏配置回退默认值

### 手动清单

自动化覆盖不到的部分，逐项手测：

- 钩子实际生效，且不与其他软件冲突
- **中文输入法组合状态下按 `Enter` 只上屏候选词，不触发保存、小条不消失。** 这是最关键的失败路径：若失效，用拼音写东西时每选一次词就会保存并关闭一次，软件完全不可用。需覆盖：拼音组合中按 Enter 选词、组合中按 Shift+Enter、组合中按 Esc
- 中英文输入法切换、候选框定位正常
- 多显示器与 DPI 缩放下的弹出位置正确
- 失焦隐藏、`Esc` 保留草稿
- `Tab` 切换：空框切搜索、有内容时缩进、搜索中切回，三个分支各测一遍
- 切到搜索再切回，记录模式的草稿仍在
- 快速连打搜索词时结果不错乱（防抖与取消生效），且扫描期间打字不卡
- 在真实规模的 `notes\`（数百个文件）上搜索，全系统键盘无可感知卡顿
- 搜索结果 `Enter` 能正确用默认编辑器打开对应日期文件
- 开机自启实际生效；移动 exe 后自启路径自动修正
- 托盘菜单各项

## 13. 已知风险

| 风险 | 应对 |
|---|---|
| 全局键盘钩子被安全软件拦截 | 提供备用组合键降级路径（第 8 节） |
| 内存超出 35MB | 若超标，排查顺序：确认未误引入第三方依赖 → 检查是否有多余的后台定时器 → 检查 RichTextBox 是否持有过大缓冲 → 检查搜索结果集是否被意外长期持有 |
| 搜索扫描阻塞 UI 线程，连带全系统键盘卡顿 | 扫描强制走后台线程（第 7 节），并以「扫描期间打字不卡」作为手测项验证 |
| 笔记规模增长后扫描变慢 | 当前设计在千级文件、几 MB 规模下足够。若将来明显变慢，先测量再考虑缓存 mtime 与内容的轻量索引——**不要提前优化**，索引会破坏内存约束 |
| `.NET Framework 4.8` 工具链限制影响开发效率 | 影响局限在语法糖与少数新库；核心 WinForms API 与 P/Invoke 无差异 |
| 双击 Ctrl 与某些软件（IDE、游戏）冲突 | 设置中可切换到组合键模式 |
